# Pocket SignalのMicroPythonサンプル

公開曲「Pocket Signal / ポケット・シグナル」（RetroFM Pocket）の全曲を、
1台のYM2203モジュールで予約演奏する。原曲はFM 3chのみで、SSGは使わない。
通常の音源カードにある「楽曲サンプル」でコードと必要な3ライブラリを新しいタブへ用意する。
「ミュート」を解除して「実行」を押す。音色と譜面はPythonの辞書・タプルなので直接編集できる。
ユーザーの既存コードと編集済みライブラリは上書きしない。
既知の同梱旧版ライブラリだけは完全一致を確認して更新し、importキャッシュを再起動で破棄する。
競合時は「バックアップして更新」で元のファイルと未保存の編集内容をプロジェクト内に残して更新できる。
`REPEAT_MS = None`なら1回だけ演奏する。`REPEAT_MS = 24 * 60 * 60 * 1000`へ変更すると
24時間繰り返す。初期値は1回のままとし、明示的に指定した場合だけ長時間演奏する。

## 移植範囲

| 項目 | サンプル |
| --- | --- |
| 音源 | YM2203、4 MHz、FM 3ch |
| 範囲 | 全64ステップ |
| 発音間隔／キーオン時間 | 180 ms／150 ms |
| 1周の期間 | 11520 ms＋余韻500 ms＝12020 ms |
| 音色 | 全chアルゴリズム7、フィードバック0。各OPの値は原曲と同じ |
| 音高 | 原曲の12音FNUM表とblock値を保持 |
| 譜面 | メロディ、ベース、和声音のMIDI番号を保持 |
| 音量 | アプリに合わせ、内蔵アンプだけ20%に調整 |

上流ジェネレーターはレジスタ順（offset 0,4,8,12）でOP値を持つ。
`fm_patch()`は論理OP1〜OP4順（offset 0,8,4,12）なので、中の2つを入れ替えて指定する。
元のFNUM表を保つため、音符の予約部分は汎用`reserve_score()`で音高を丸め直さず、
I2C予約命令へレジスタ値を送る。音源コアは変更しない。

960イベントを1パケット最大63件へ分け、最後に32ビット期間のplayを一度だけ送る。
960件の固定パターンを使い、`sleep_ms()`の実行間隔に発音を依存させない。
繰り返し時は1周のパターンを音源側で再利用し、I2CやPythonを周期的に動かさない。
Python終了後も予約は最後まで進む。停止・再起動・例外・切断・背景移動で消音する。
曲全体を扱う汎用VGMプレイヤーやMMLコンパイラーは、このサンプルでは追加しない。

## 検証

固定MicroPythonでサンプルを実行し、原曲VGMから読み取った全960イベントと時刻が
完全一致すること、FM音色のレジスタ値が一致することを単体テストする。
固定ymfmコアの48 kHz PCMは、原曲の冒頭を同じアンプ値で再生した参照と、
全曲の予約終了後を含めて一致する。SSG出力は0。これは同じコアでの比較であり、実チップや
別のエミュレーターとの音質一致を示すものではない。

製品版Chromeで、楽曲ボタン、実音声、予約の完了・消音、ライセンスを含むコードと
ライブラリの保存・復元、再演奏とホスト停止を検証する。

2026-10-11の検証では、全単体テスト282項目（53ファイル）、型検査、通常・Sakura配信用ビルド、
第三者通知と固定音源コアの検証が成功した。最終配信用ビルドで通常音源・音色編集・連続試聴の
Chrome E2E15項目が成功した。PC幅1360px・モバイル幅390pxで楽曲ボタンと再生状態表示を確認した。
この新しい楽曲サンプルのEdge上での操作と実スピーカーでの確認は未実施。

2026-10-12の全曲・長時間対応では、単体296項目（53ファイル）、型検査、通常・Sakura配信用
ビルド、第三者通知・固定音源コアの検証が成功した。最終配信用ビルドで音源関連Chrome E2E27項目が成功し、
24時間指定の2周目、追加I2C送信なしの継続、停止・再起動、既知の旧ライブラリ更新と編集済みタブの保護を確認した。
PC幅1360 px／モバイル幅390 pxで24時間表示を確認した。24時間の終了境界はサンプル時計を進めて検証しており、
24時間の実時間連続運転や今回の変更のEdge上での検証は未実施。
