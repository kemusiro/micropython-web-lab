# ADR 0051: 実験セットの保存と切替を一括で確定する

- 状態: Accepted（E1の保存基盤。通常画面への接続はE2）
- 日付: 2026-10-19

## 背景

題材ごとにコード、ファイル、配線、開始条件、表示設定を保持するため、保存単位を現在の
単一プロジェクトから実験セットへ広げる。コードと配線を別々に切り替えると、一方だけが
保存された状態や、前の実験の遅延通知で新しい実験を上書きする状態が生じる。

E0で用意したファイルと編集バッファの分離を維持し、保存と切替をUIから独立して検証する。
現行画面はこの段階では従来のプロジェクトと配線を使用する。E2で入口と作業画面を接続し、
新しい保存経路への移行もまとめて有効にする。

## 決定と代替案

| 項目 | 採用する方式 | 比較した方式 |
| --- | --- | --- |
| 保存先 | 既存DBを版2へ拡張し旧ストアを残す | 別DBは元セット・新セット・選択先の一括確定ができない |
| 保存単位 | バイト、編集バッファ、構成をセットIDで一レコードにする | localStorageの複数キーでは部分保存を取り消せない |
| 競合 | 書込トランザクション内でrevisionを比較する | 保存日時や後勝ちでは別ウィンドウの編集を失う |
| 切替 | 実行を停止し、保存成功後に新しい世代を起動する | Workerを常駐させる方式は背景実行とメモリ管理が増える |
| 失敗 | 保存失敗なら編集を保持して停止状態、起動失敗なら新セットを保持する | 保存後に旧実行へ戻したように表示すると実際の状態と一致しない |

## DBとレコード

`ProjectDatabase`が`micropython-web-lab-project`を版2で開く。`project`ストアは残し、
`experimentSets`と`experimentWorkspace`を追加する。旧`ProjectStore`もこの接続管理を使い、
版1で開き直す経路は持たない。`blocked`は失敗として通知し、後から阻止が解消しても
その要求で勝手に移行しない。`versionchange`では接続を閉じ、利用側に再読込を求める。

利用者レコードの`recordVersion`は1。ID、revision、タイトル、作成・保存日時、配布元または
旧形式の出自、実行基盤のID・版・ハッシュ、ファイル、編集バッファ、構成、開始条件、
実行方針、観察表示、任意の未適用配線を持つ。Worker、Python変数、音声予約、実測系列は含めない。
数値は有限値、参照は登録用の識別子と版として扱い、構造検証は実行許可と区別する。

E1はボード型と、旧配線を復旧するための実行不可状態を扱う。物理モデルの構成や時間方針は
E3以降に型と版を設計して追加する。専用の実行APIやDevice API v1はここでは変更しない。

## 保存と移行

`ExperimentStore.save`は渡されたIDとrevisionをトランザクション内の保存済みレコードと比較し、
一致する場合だけrevisionを一つ進める。保存日時を変えても競合判定へ影響しない。
通常保存では選択先を更新しないため、別ウィンドウで最後に選ばれたセットへ書込先が追随しない。

移行は旧`project/current`を同じトランザクションで読み、最新の旧レコードを元にする。
現行の時刻比較による終了時退避の復元は移行時に一度だけ適用し、バッファにだけ反映する。
新しい無題タブへパスを割り当てない。新セット、選択先、移行元識別情報を一括保存し、
再試行では完了情報を見て同じコピーを増やさない。旧IndexedDBレコードとlocalStorageキーは削除しない。

移行後は旧`ProjectStore`の読書きを拒否する。E2の画面接続では、ファイル保存、Pythonの
チェックポイント、下書き、配線適用をすべて同じコーディネーターへ接続する。
旧配線が不正なら、呼出元は`unavailable`構成を明示してコードを移行し、原本を保持する。
未知のレコードは自動変換や上書きを行わず、読取専用の回収APIで原データへ到達できる。

## 切替と遅延処理

1. 候補と現在の編集を検証し、ホストに実行能力の確認を求める。この間は実行を維持する。
2. 入力をロックして既存の保存キューを確定させる。準備段階までの取消だけを受け付ける。
3. 世代を進め、ホストからWorker・音声を停止し、押下入力を解除する。
4. 受信済みのファイルと最新バッファを取り、元セット、新規候補、選択先を一括確定する。
   既存候補のrevisionも再確認する。トランザクション内でモデルやアセットの読込を待たない。
5. 保存成功後に構成とコードをまとめて反映し、新しい初期状態の実行環境を用意する。
   コードは自動実行しない。

保存完了はIDBトランザクションの`complete`で判断する。`ExperimentProjectPersistence`は
セットIDと世代へ固定した保存ポートであり、旧ポートの遅延書込を新しい選択先へ流さない。
保存失敗時は元セットの編集を保持し、新しい世代の停止状態へ結び直して再試行できる。
起動失敗時は確定済みの新セットを保持し、旧セットへ巻き戻さない。

ホストは能力確認、UIロック、外部からの強制停止、音声破棄、入力解除、表示の反映、
初期状態の起動を実装する。非同期完了時にもセッションID・世代を確認する。
E1のテスト用ホストを実際のMicroPython起動に接続したとは扱わない。

## 上限と退避記録

ファイルは4 MiB、1,024エントリ、パスはUTF-8で240バイト。エディタは24タブ、
一タブ200,000文字、配線は64 KiBの既存上限を使う。新規作成は16セット、合計64 MiBまでとする。
合計はファイルのバイト列と、その他のフィールドをUTF-8のJSONにしたサイズの合計とし、
バイナリをJSONの数値配列へ展開して数えない。ブラウザのディスク使用量や保存保証ではない。
上限を超えた既存データの読出しと縮小を許し、利用者データを自動削除しない。

新しい終了時退避は版1、256 KiBまでとし、セットID、基準revision、タブを持つ。
同じID・revisionにだけバッファを復元し、ファイルの対応パスを変更させない。
保存成功後の削除は退避内容も照合し、保存待ちの間に書かれた新しい退避を消さない。
容量超過は切り詰めず拒否し、直前の退避を残す。

## 検証と運用上の制約

新規の単体テストはスキーマ、UTF-8容量、退避記録、切替順序、取消、遅延保存、起動失敗を扱う。
`pnpm test:e2e:experiments`では実際のIndexedDBを使い、移行・切替の各書込後のabort、
二ウィンドウの競合、旧保存との競合、DB更新、容量超過、未保存表示の保持を検証する。
テスト用ページは開発サーバーだけで使い、本番ビルドへ含めない。

保存時は全セットを読んで検証・容量計算する。E2の有効化前に、最大件数付近とモバイル端末で
保存頻度・所要時間を測り、必要なら容量台帳などを同じトランザクション内で管理する方式を比較する。
複数ブラウザでの移行と画面の回収導線もE2の確認対象とする。

DBの版は引き下げない。版1を明示して開く旧配布版への巻戻しでは`VersionError`になる。
移行後の配布を戻す必要がある場合は、DB版2と新レコードを読める版を用意する。
