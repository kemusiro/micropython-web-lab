# ADR 0048: YM2203予約の正式上限を131,071イベントへ拡張する

- 状態: Accepted
- 日付: 2026-10-12

## 背景と選択肢

全曲を予約したいという要求に対し、従来1,024件は音色・変調の更新が細かい楽曲で不足する。
利用者は65,535件などへの正式拡張を許容した。検証用の全曲ログは123,131件で、
65,535件へ増やしても収まらない。65,535件と逐次予約切り替え、131,071件の単一予約、
汎用ストリーミングを比較し、131,071件の単一予約を採用する。
これにより全曲をAudioWorkletのサンプル時計で再生し、演奏中のPython時計や予約交換を避ける。
ゲームの楽曲データはローカル検証用の別成果物とし、WebLab配布物・公開リポジトリに同梱しない。

## 決定と互換性

Device Model・内部Runtimeメッセージ・AudioWorklet・Python予約APIは、上限を131,071件とする。
uint32時刻・期間、同時刻の登録順、loopの100 ms以上という条件は変更しない。
I2Cの`00`〜`06`、1回の転送256バイト、`05`の最大42件は維持する。
プロトコル版・Device SDK・保存形式・音源コア・依存パッケージは変更しない。

旧`readfrom(0x44, 4)`は `[1, min(件数,65535)のlow, high, アンプ]` を返す。
65,536等で0へ折り返さず、旧ドライバーの空キュー判定を壊さない。
新`readfrom(0x44, 6)`は `[1, count0, count1, アンプ, count2, count3]` を返す。
Pythonの`status()`は6バイトを要求して正確なuint32件数を復元する。
旧モデルは追加バイトを0で埋めるため、旧容量内では新しいstatus読み取りも成立するが、
大容量データを古い配布版へ送ると拒否される。利用者は配信更新後にページを再読み込みする。

1,024件版ドライバーの正本を`src/drivers/pre-large-reservations`へ未変更で保存する。
旧長時間拡張前の正本も残す。サンプルを開く際の更新は、いずれかの既知旧版との全文一致、
かつ未編集タブとの一致に限る。編集版・shadowing・未保存変更は保護し、既存の明示的バックアップ操作を使う。

## 資源・セキュリティへの影響

予約キューへの追加で全イベントを毎回コピー・検証する処理は、大容量の小分けI2C転送で二乗時間になる。
新バッチの形式・上限・時刻順と旧キュー最後の時刻だけを検証し、拒否後の状態を維持してから追加する。
play時だけ所有権を分離するコピーを作り、転送拒否なら未再生キューを維持する。

1パターンは最大393,213数値。8バイト換算で約3 MiBのJavaScript配列となり、各通信コピーや
エンジン固有のオーバーヘッドが別に加わる。固定2 MiBの音源WASM・1 MiBのMicroPythonヒープは増やさない。
Pythonの大量tuple/listは音源容量より先に固定ヒープを使い切り得る。
大容量の生レジスタ列は6バイト/件のバイナリをファイルから最大252バイトずつ読み、`05`へ転送する。
PCMや繰り返し期間分のイベントを蓄えない。

現行の同期JavaScriptプロキシが反復バッファ転送中にGCを起動すると、Asyncify importエラーになる。
Pythonドライバーと全曲検証プログラムは16バッチごととstatus前にPython側で`gc.collect()`し、ブリッジ内のGCを避ける。
これはランタイムの暫定対策であり、I2Cの正式要件ではない。
バッファ境界がGCの中断を安全に扱えるようになった時点で、この先行GCを削除できる。
ドライバーメソッド内のGCで4 KiBのAsyncify退避領域が不足するため、variantの
`ASYNCIFY_STACK_SIZE`を固定64 KiBへ増やして固定版ランタイムを再ビルドする。
これはGC時のWASM Cスタック退避領域であり、Pythonヒープ・Pythonからの権限は変更しない。
生成物は直接編集せず、固定ツール・アーカイブ・既存パッチを使いハッシュを再記録する。

Workerの累積音声値予算は `131071 * 3 + 32768 = 425981` とする。
最大予約1回と従来の即時制御予算を受け入れる。累積命令1,024件、未受付命令256件は維持する。
stopで予算は補充せず、再起動を要求する。新たなネットワーク・DOM・ストレージ権限は公開しない。

更新密度によってCPU負荷は変わる。同時刻に極端に大量の命令がある場合まで無音切れを保証しない。
全曲サイズの通常入力を検証し、手動停止・切断・背景移動・AudioContext中断で消音する仕組みを維持する。
極端な入力への対策として、無制限容量や汎用ストリーミングではなく明示上限と累積送信予算を採用する。

## 検証

- 65,536件と131,071件のstatus、旧4バイト飽和、131,072件の原子的拒否、バッチ間の時刻順。
- RuntimeとAudioWorkletのメッセージ上限、送信予算、停止による予算リセットの禁止。
- 旧同梱ライブラリの更新と編集版の保護、1,024件を超えるPython予約。
- ローカル全曲ログとの全レジスタ・時刻・PCM比較、固定1 MiBヒープでのバイナリ転送、音源側ループ。
- ブラウザで全曲サイズの受付、FM/SSG出力、実時間の完了、停止・再起動。

24時間の実時間連続運転と実チップとの比較は今回も対象外。

2026-10-12: 単体306項目（54ファイル）、固定ランタイム・通知の検証、型検査、
通常・Sakura配信用ビルドが成功。別のローカル全曲テスト4項目で、固定1 MiBヒープからの
123,137件の転送、元ログとの全レジスタ・時刻・全曲PCM一致、音源側ループと失敗時の破棄を確認した。
Chromeでは約5分の全曲を実時間で最後まで演奏し、全イベントの適用・完了・消音・保存後の復元を確認した。
最終ビルドでも全曲の24時間設定の受付・出力・停止・再起動が成功した。

ブラウザ回帰85項目のうち84項目が成功。残る連続予約のテストは、Workerの固定待機時間で
AudioWorkletの完了表示を予測するため初回メーターを取りこぼした。
テストを音声の完了・反映通知を待って次の予約を送る方式へ直し、当該項目が3回連続で成功した。
合成データによる131,071件の最大容量、旧status飽和、MicroPythonからの停止・再起動も検証した。
